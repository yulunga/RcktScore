## Authoritative flow

1. The signed-in iOS app requests its purchase context from the backend.
2. The backend authorises the organisation membership, creates or returns one
   stable random UUID (`appAccountToken`) for that personal account, and returns
   the allowed Personal Plus product IDs.
3. iOS calls StoreKit with `.appAccountToken(token)`.
4. StoreKit returns a locally verified transaction. iOS sends its signed JWS to
   the authenticated verification endpoint. Local verification alone never
   changes the Hit n Score plan.
5. The backend verifies Apple's certificate chain and JWS, then validates the
   bundle ID, Apple app ID, environment, product ID, account token, transaction
   dates and revocation state.
6. In one database transaction it stores the transaction/event idempotently,
   derives the entitlement, updates `SkwshOrgSettings.plan` if required, and
   appends an immutable audit row.
7. Only after the backend acknowledges the verified transaction does iOS finish
   it and refresh its dashboard/session entitlement.
8. App Store Server Notifications V2 and periodic reconciliation feed the same
   lifecycle processor, so all paths use identical validation and plan rules.

Apple returns the same UUID in later transaction and renewal information, which
is why the token must be generated by this backend and remain stable for the
account. See [Apple's appAccountToken documentation](https://developer.apple.com/documentation/appstoreserverapi/appaccounttoken).

## Required backend API

### Authenticated account context — implemented, deployment pending

`GET /subscriptions/apple/context/{organization_id}`

- Require a valid organisation-user bearer session.
- Require membership of the requested personal organisation.
- Generate the UUID once and return the existing value thereafter.
- Return server entitlement, monthly/yearly product IDs and whether purchasing
  is currently enabled.
- Never accept an account token supplied by the client as the account mapping.

### Authenticated purchase verification — implemented, deployment pending

`POST /subscriptions/apple/verify`

- Accept `organization_id`, `signed_transaction`, and `signed_app_transaction`.
- Apply the same membership checks as the context endpoint.
- Verify and decode the JWS with Apple's official App Store Server Library.
- Require the decoded `appAccountToken` to match the organisation's stored UUID.
- Allow only the configured bundle/app/product identifiers.
- Upsert by original/latest transaction IDs and make repeats safe.
- Run the lifecycle processor and return the new server entitlement.
- Reject invalid, mismatched, revoked or unsupported transactions without
  changing the plan.

### Apple notification receiver — implemented, deployment/configuration pending

`POST /subscriptions/apple/notifications`

- This endpoint is public because Apple cannot send a Hit n Score user session.
  Its authentication is successful Apple JWS verification, not a shared header.
- Verify the outer `signedPayload` and nested transaction/renewal JWS before use.
- Deduplicate by `notificationUUID` and tolerate duplicate or out-of-order events.
- Resolve the account through the verified `appAccountToken` and original
  transaction ID, then invoke the same lifecycle processor.
- Return a success response only after durable/idempotent acceptance; log and
  monitor invalid payloads without storing them as trusted events.

Apple's Python library supports signed-data verification and the App Store
Server API: [apple/app-store-server-library-python](https://github.com/apple/app-store-server-library-python).

## Entitlement state rules

The database, not the device, is authoritative.

| Verified state/event | Account plan |
| --- | --- |
| Initial buy, resubscribe, valid renewal | `personal_plus` through verified expiry |
| User turns off auto-renew | Keep `personal_plus` until the paid expiry date |
| Billing grace period | Keep `personal_plus` until verified grace expiry |
| Billing retry without active paid/grace access | `personal_free` |
| Voluntary expiry, billing-retry expiry, grace-period expiry | `personal_free` |
| Refund or revoke | `personal_free` from Apple's revocation effective time |
| Refund reversed and transaction is otherwise valid | Recalculate and restore `personal_plus` |
| Unknown, invalid or mismatched payload | No entitlement change; alert for investigation |

At minimum process `SUBSCRIBED`, `DID_RENEW`,
`DID_CHANGE_RENEWAL_STATUS`, `DID_FAIL_TO_RENEW`,
`GRACE_PERIOD_EXPIRED`, `EXPIRED`, `REFUND`, `REFUND_REVERSED` and
`REVOKE`. Apple's notification reference defines the event/subtype meanings:
[notificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype).

## Database additions

Migration `027_apple_subscription_lifecycle_processing.sql` completes the model with:

- a stable, unique `app_account_token` attached to the personal organisation;
- raw and decoded transaction metadata needed to reproduce the entitlement;
- `last_verified_at`, `last_reconciled_at`, processing error and retry metadata;
- an append-only `subscription_entitlement_audit` table containing account,
  old/new plan, effective time, reason, source (`purchase`, `notification`,
  `reconciliation`, `admin`), notification UUID, transaction IDs, actor/request
  ID and creation time;
- indexes for account token, original transaction, expiry, status and stale
  reconciliation queries.

Do not overwrite audit records. Store sensitive Apple credentials in AWS Secrets
Manager, never in the migration, SAM parameters, source control or Lambda logs.

## Reconciliation and operations

- The EventBridge Scheduler runs hourly. It enforces locally known expiry/grace
  deadlines even when Apple is unavailable, then reconciles due subscriptions.
- Call `Get All Subscription Statuses`; use transaction/refund history when the
  status is ambiguous. Apple also provides notification history for missed
  deliveries. See the [App Store Server API](https://developer.apple.com/documentation/appstoreserverapi).
- Feed verified results into the same lifecycle processor and audit every change.
- Retry transient Apple/database failures with bounded backoff and a dead-letter
  queue; alarm on DLQ messages, invalid-signature spikes, reconciliation lag,
  webhook 5xx rates and entitlement drift.
- Add structured logs containing request/notification/transaction correlation
  IDs but no private key or full session token.

## Root-admin subscription activity

`/rckscoreAdmin/subscriptions` shows:

- effective Hit n Score plan and whether it is Apple-managed or an admin override;
- product (monthly/yearly), verified status, environment, expiry/grace date,
  auto-renew status, original transaction ID and last verification/reconciliation;
- chronological Apple lifecycle activity and entitlement audit entries;
- visible drift and processing/reconciliation errors. Manual root-admin plan
  changes append an audit record without modifying Apple's transaction ledger.

Root admins cannot cancel an Apple subscription for the customer; the app should
continue linking customers to Apple's Manage Subscriptions screen.

## Configuration checklist

### Deployment sequence

1. Apply `backend/schema/027_apple_subscription_lifecycle_processing.sql` in
   Supabase before deploying these Lambdas.
2. In App Store Connect, create an In-App Purchase key under **Users and
   Access → Integrations → In-App Purchase**. Download the `.p8` once and note
   its key ID and issuer ID.
3. Create one AWS Secrets Manager JSON secret in `eu-west-2` with keys
   `private_key` (the complete PEM text), `key_id`, and `issuer_id`. Never put
   these values in `samconfig.toml` or Git.
4. Add `AppleServerApiSecretArn="<the-secret-arn>"` to the existing local
   `parameter_overrides` in `backend/samconfig.toml`, then run `sam build` and
   `sam deploy` from `backend/`.
5. Configure the App Store Connect Sandbox V2 URL as
   `https://st3nn5zsm6.execute-api.eu-west-2.amazonaws.com/prod/subscriptions/apple/notifications`.
   Keep `AppleAllowedEnvironments="Sandbox"` while running the lifecycle suite.
6. Enable Billing Grace Period for Sandbox testing and exercise renewal,
   cancellation, retry/grace, expiry, refund/revocation and a missed-event
   reconciliation. Confirm `/rckscoreAdmin/subscriptions` after each case.
7. Only after Sandbox evidence passes, configure the Production V2 URL and
   change `AppleAllowedEnvironments` to `Sandbox,Production` for the release
   transition.

- [ ] Monthly/yearly products use their exact production IDs and one subscription group.
- [ ] In-App Purchase key created; issuer ID, key ID and `.p8` private key stored in Secrets Manager.
- [ ] Apple root certificates packaged from Apple PKI and maintained with a documented rotation path.
- [ ] Bundle ID and numeric Apple app ID configured separately for Sandbox/Production verification.
- [ ] Sandbox and Production Server Notifications V2 URLs configured in App Store Connect.

## Required test evidence

- [ ] Invalid signature, wrong bundle/app/product/environment/token are rejected.
- [ ] Initial monthly/yearly purchase upgrades the correct signed-in account only.
- [ ] Duplicate purchase and duplicate notification are idempotent.
- [ ] Out-of-order older events cannot overwrite a newer entitlement.
- [ ] Renewal extends expiry; auto-renew cancellation keeps access until expiry.
- [ ] Grace entry/exit, billing recovery and failed retry follow the chosen policy.
- [ ] Refund/revoke downgrades and refund reversal recalculates access.
- [ ] Restore on another device maps to the correct Hit n Score account.
- [ ] Missed notification is repaired by reconciliation.
- [ ] Apple sandbox test notification and TestFlight purchase both reach production-like infrastructure.
- [ ] Root-admin status and audit match the database after every scenario.
- [ ] A Free account cannot gain Plus by changing a device response or replaying a JWS from another account.

Production purchasing is ready only when every configuration and test box is
complete and the Release build no longer contains the current Debug-only guard.
